# Creator source authority boundary — review draft

This is an incomplete, fail-closed integration. Do not deploy or apply the SQL draft without a separate review and a verified record-issuing workflow. No production migration is applied by this change.

## Independent checks

1. Authenticate the user and load the owned CreatorLab project server-side. Define the exact normalized editorial snapshot to be verified; its SHA-256 covers claim identity, scope, evidence, source metadata, readiness and any counter-evidence review. SHA-256 is an identity, not proof of trust.
2. Acquire each source on the server using the existing pinned-DNS HTTPS acquisition (`originalSourceAcquisition.server.ts`). Its URL/IP/redirect restrictions and content limits remain mandatory. `verifyOriginalSourceEvidence` checks the exact passage against the acquired bytes and records document fingerprint and location. Unsupported PDF, redirects that fail identity checks, normalized-only matches and unavailable content require review; none become verified automatically.
3. Independently establish whether the retrieved document is the actual original research or a primary document. A successful fetch, an exact quote, a domain name, retrieval lane, paper label or client-provided `authority` is not sufficient. The current acquisition function accepts `authority` as a parameter and cannot establish this fact. A future server-owned qualification method must use verifiable original-publication provenance or an authorized human review, retain the supporting basis and reject ambiguous cases. Until it exists, never issue `original_research` or `primary_document` records.
4. Only after server-owned verification should a privileged server writer insert one record per evidence item with the authenticated owner, owned project, exact snapshot digest, source/evidence identities, source/passage digests, document digest, qualification method and bounded expiry. Neither a client endpoint that accepts a classification nor a client-writable row is sufficient. Review how the snapshot is frozen and approved before implementing any writer; a writer must not certify arbitrary user-provided claims merely by hashing them. Exact passage matching does not establish semantic support, scientific accuracy, or claim entailment.

## Generation boundary

The route checks project ownership, reads records with the server-only service client, and validates every evidence item's owner, project, snapshot, source, passage, verification state and expiry. Claims with primary obligations additionally need an independently qualified primary record among their supporting evidence. The existing grounding, readiness and scientific gates still run afterwards. A missing table, record or classification blocks generation. The owner/snapshot validation also prevents copied records from becoming authorization.

The SQL is a *draft*, outside the migration directory. Its table uses RLS plus explicit revocation from `public`, `anon` and `authenticated`; service role access must remain server-only. Before generating or applying a migration, test grants and RLS with all actual roles on an isolated database and confirm project ID typing and deletion/retention policy. There is deliberately no record writer or backfill here, so existing historical records are not reclassified. A deployment of this draft as-is would block research-backed generation.

## Remaining work

Implement and independently review source qualification, secure snapshot freezing and record issuance, verify passage/claim semantic support separately, test the actual API with a disposable database and role-specific RLS tests, and exercise server-owned retrieval against representative first-party and non-first-party sources. Only then generate and review an additive migration and plan rollout. This draft does not grant Evidence Review exemptions and cannot establish scientific truth.

## Claim-specific offline prototype

`sourceAuthorityIssuance.ts` contains a dependency-injected preparation core for synthetic review tests only. It requires an authorization decision before acquisition, checks the cited passage against a `trusted_fetch` document with the source authority forced to unknown, and asks for a claim-specific human judgment including publisher authorship and rationale. It records reviewer identity, authorization basis, exact document fingerprint and expiry. Injected callbacks are not a security boundary: no production CLI, reviewer authorization, immutable owned snapshot reader, or privileged writer is implemented. The claimed acquisition state must never be accepted from an untrusted caller.

Records are now scoped to claim/evidence pairs, including non-supporting links. A primary finding for one claim cannot automatically qualify another claim. Human classification is an editorial decision, not proof of truth or semantic entailment. The offline tests use synthetic data and simulated reviewer decisions, not the saved METR project or an actual human review.

The draft now includes a separate server-owned snapshot table. Generation compares owner, project and a canonicalized SHA-256 digest of the stored JSON against the normalized submitted context before reading claim-scoped verification records. Canonical object-key ordering accounts for JSONB reordering. The table and its grants are not applied or verified against Postgres. No snapshot creation workflow is implemented: inserting a client-supplied snapshot without an authorized review/freeze protocol would not make its scientific contents trustworthy.

## Disabled-by-default implementation

The earlier statements about missing workflow bindings are superseded by `sourceAuthorityWorkflow.server.ts` and `/api/creator-source-authority`. The route is disabled unless `VELTO_SOURCE_AUTHORITY_ENABLED` is exactly `true`. Server-side Supabase Auth validates the bearer token and the authenticated user ID must also appear in the server-managed `VELTO_SOURCE_AUTHORITY_REVIEWER_IDS` allowlist. Neither user metadata nor a request reviewer ID is used. Authorized reviewers may freeze a normalized context against an owned CreatorLab project, inspect a freshly acquired exact passage and then issue a claim-specific decision bound to the inspected document digest. Issue fetches and checks the source again; a changed digest rejects the review. The SQL remains an unapplied draft; no database, RLS, real reviewer, or real fetch has been tested in this change. Server owners must configure the feature and reviewer allowlist only after isolation and access testing. Human review is an editorial decision, not scientific proof.
